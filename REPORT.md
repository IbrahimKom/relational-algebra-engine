## Methodology

- `perf/datagen.py` generates `R(a, b)` and `S(b, c)`: `a`/`c` are just the
  row index, `b` is drawn uniformly from a domain of size
  `D = round(n_s / match_rate)`, so a given R-tuple is expected to match
  `match_rate` S-tuples. Section 8.3's main table uses `match_rate = 1.0`.
- `perf/run_experiment.py` loads the generated `.ra` files through the
  engine's normal tokenizer/parser (so the load itself exercises the real
  system, though load time is *not* included in the timed portion), then
  times exactly one call to `evaluate()` for `R join[R.b=S.b] S` with
  `time.perf_counter()`, and reads `join_compared` off
  `src.interpreter.COUNTERS` immediately after.
- `join_compared` is incremented as `len(left.tuples) * len(right.tuples)`
  at the point of evaluating a `Join` node -- i.e. once per pair the
  nested loop actually visits, computed directly rather than incremented
  in a loop (see DESIGN_LOG.md, "AI assistance issue #2" -- an earlier
  draft double-counted this).
- To reproduce: `python -m perf.run_experiment --out perf/results.csv`
  (add `--sizes` / `--match-rate` / `--seed` to change the run). The
  script writes each row to the CSV as it completes, so a partial run's
  results survive an interruption.

## 8.4 — Analysis

### Q1. Relationship between n, m and the comparison count

**Prediction (to verify against the table above):** for a nested-loop join
with no index, every one of the `n` tuples in `R` is paired with every one
of the `m` tuples in `S`, so `comparisons = n * m` exactly -- there is no
approximation here, since `join_compared` is computed as
`len(R.tuples) * len(S.tuples)` directly. *To fill in once the table is
complete: confirm each row's `comparisons` column equals `n*m` exactly,
and note there's no discrepancy to explain precisely because the count is
computed as that product rather than sampled or estimated.*

### Q2. Wall time vs n on log-log axes

*To fill in: plot `wall_time_s` vs `n` on log-log axes once the table is
complete (a small script using matplotlib against `perf/results.csv` is
enough -- assignment allows a plotting library for the report). Since
`comparisons = n^2` for this experiment (m = n throughout) and each
comparison does roughly constant work, the expected slope on a log-log
plot is close to 2 -- a slope of k on log-log axes means
`time ∝ n^k`, and k≈2 is exactly what an `O(n*m)` = `O(n^2)` (at m=n)
algorithm predicts.*

### Q3. Select and project at the same sizes

*To fill in from `perf/results.selectproject.csv` (generated alongside
the main table). Expectation to check the real numbers against: `select`
is `O(n)` -- it examines each of R's `n` tuples exactly once, so its time
curve should be roughly linear in n and dramatically flatter than the
join's quadratic curve; `project` is also `O(n)` to build the projected
tuples, plus whatever overhead the underlying `set` incurs deduplicating
them, so it should track `select` closely (both single passes over R) but
end up marginally more expensive by a set-hashing constant.*

### Q5. Does match rate change the comparison count? The wall time?

**Measured** (supplementary run, n=m=3000, seed=7, four match rates,
`perf/match_rate_results.csv`):

| match rate | domain size | comparisons | wall time (s) | output tuples |
|---|---|---|---|---|
| 0.5 | 6000 | 9,000,000 | 13.26 | 1,470 |
| 1 | 3000 | 9,000,000 | 12.74 | 2,872 |
| 5 | 600 | 9,000,000 | 12.78 | 15,076 |
| 20 | 150 | 9,000,000 | 12.47 | 59,728 |

**Comparison count: no** -- it is exactly `n * m = 9,000,000` at every
match rate, because a nested-loop join has no way to know which pairs
will match without first generating and testing them; it evaluates the
condition on literally every pair regardless of how selective that
condition turns out to be.

**Wall time: essentially no**, for the same reason -- the work per pair
(build the concatenated tuple, evaluate one equality comparison, maybe add
to the output set) doesn't depend on whether that pair happens to match.
The small variation across rows above (~6%) is noise, not a trend with
match rate -- if anything the highest match rate (most output tuples, so
the most `set.add` calls) has the *lowest* time here, confirming the
variation isn't driven by output size either. *(Note: this supplementary
run executed concurrently with the main 8.3 background run, competing for
the same CPU, which is the likely source of that noise -- rerun in
isolation if a cleaner number is wanted.)*

**Why the two answers are the same:** both come from the same root cause
-- a naive nested-loop join has no shortcut that lets selectivity reduce
its work. An index or a hash join *would* make match rate matter (fewer
matches → less time spent on the matching/output-building step even
though the probe cost might stay proportional to input size), but that's
exactly the class of technique this project's scope excludes (Section 3:
"Indexes, hash joins and sort-merge joins are likewise excluded").

### Q6. What would make the million-tuple join feasible?

*To fill in as a short paragraph. Sketch: an index on the join column
(e.g. a hash index on `S.b`) turns the per-R-tuple cost from "scan all of
S" (`O(m)`) into "look up matching S-tuples directly" (`O(1)` amortized
per match), taking the whole join from `O(n*m)` to roughly
`O(n + m + output size)` -- which is the entire reason indexes and
hash/sort-merge joins exist, and exactly the material the assignment says
later bonus projects will build on top of this one.*
